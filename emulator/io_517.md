```
...
```

Looks like it expects some incoming data on port A, strobed on CA1. That's offset 0x000ba446 in `fcontrol` process.

By stepping through instructions, it looks like it expects a sequence of 6 bytes, all with MSB set. There is a timeout wait of 6.48ms (assuming a 16 MHz CPU) between two bytes; if a timeout occurs, the function returns early.

Once the 6 bytes are received, the first byte is ANDed with $7C then divided by 4 (so, 5 bits) then stored to A7+$26.

The lower 2 bits are shifted left by 14 bits, then added to the second byte after being shifted left by 7 bits (overwriting the least significant of the original 2 bits?) then added to the third byte.

```
00000000 11111111 22222222 33333333 44444444 55555555
.6543210 76543210 76543210 ......10 76543210 76543210
 |---||- -------- -------|       |- -------- -------|
 (A7+26)       (A7+2A)                 (A7+3A)   

(A7+26) = $8089912
(A7+2A) = $80899CC
(A7+3A) = $80899C8
```

Those look like X-Y coordinates combined with info like buttons pressed.

Is that a mouse? No, it's the bitpad (aka digitizer)!!

This is also confirmed in Aesthedesbekabeling.jpg.

## Port C (keyboard)

When port A is strobed, a 12-bit code is obtained by concatenating the lower nibble of port A and the contents of port B.

86F0DC0: there's some sort of array at A6+$3a88, 2 bytes of each entry, indexed by the keycode, size 3500 entries.

Entries with values $F0, $F1, $F3 or $F4 have some special treatment.

867C390: If the value is less than $100, then there's another lookup (`keyboard_keycode_types`). Probably, those values map to keys of the mechanical keyboard.

I've saved the keycodes table as binary file `keycodes_table.bin`. And I made a script (via Copilot) to convert that table in CSV, Markdown, C array or YAML for further investigation:

```
$ python3 print_keycodes_table.py --help
usage: print_keycodes_table.py [-h] [-f {csv,markdown,c,yaml}] [-u] [-s {keycode,command}] [path]

Read a 16-bit keycode table and print non-0xFFFF mappings.

positional arguments:
  path                  Path to the binary file containing the 16-bit table

options:
  -h, --help            show this help message and exit
  -f {csv,markdown,c,yaml}, --format {csv,markdown,c,yaml}
                        Output format: CSV (default), Markdown, C array or YAML
  -u, --uniquify        Discard duplicate command IDs, keeping only the lowest keycode for each command.
  -s {keycode,command}, --sort {keycode,command}
                        Sort output by keycode (default) or by command ID.
```

I've modified the keyboard emulator (`aesthedes_keyboard.cpp`) so that it sends one keycode per second using the C array output from that script. By looking at the changes in the data control monitor (i.e. the middle B/W screen), one can discover the meaning of each keycode. I created a "database" YAML file at `keycodes.yaml`.

Do note that some keycodes bring the UI into a state where it doesn't accept any but some specific inputs (other keystrokes or bitpad inputs). Therefore, the scan must be done in several "rounds" where each round sends other keycodes than the ones sent in the previous rounds. Eventually, all keycodes will be discovered.

After several rounds, I realize that some keycodes have no effect due to the state the system is, caused by other actions. For example, no-one of the alphanumeric keys have any effect unless an action has a text prompt (for example keycode 1485 for deleting files). So, I switched to a different approach where the keycodes are received via a TCP/IP socket I can connect to via `nc` and manually type keycodes.

Some details:

* Keycode 523 is ESC. One can send this to leave any text-prompt state.
* Some low-numbered command IDs map directly to ASCII characters. For example keycode 1063, mapped to command ID 0x20, is the spacebar.
* The upper-case alphabet is missing (except for the letter E), but the lower-case alphabet is present.
* The keys for layer 0 to 63 have command IDs 0x044c to 0x048b respectively.

### Opening a file

From YouTube video "[The US$ 300k Aesthedes 2 startup and loading files. The only working one in the world](https://www.youtube.com/watch?v=ksrPnci9ihg)":

1. User presses From Disk
2. Screen shows "Press ENTER to confirm"
3. User presses Enter
4. Screen shows "Give FileName"
5. User types file name, e.g. `ebt`

Which keycode is Enter? It is in the same column of To Disk and From Disk. Their keycodes are 1355 and 1354 respectively, and their command IDs are 0x0655 and 0x0656.

Keystrokes with similar keycodes or command IDs have no action. So I went the brute-force route: automating the injection of From Disk (1354), then each one of the keycodes I haven't seen an action for (we see the effects of Enter only when prompted), then ESC/Abort (523), then repeat with the next keycode. While a script (`find_enter_keycode.py`) injects the keycodes via the TCP socket, I look at the screen, stopping the script once the file name prompt is shown. And I do stop it when the keycode sent is 554 (command ID 0x1f5). Therefore, Enter is 554.

After typing the file name, the screen shows "Loading: ebt" and "Loading all levels" but it gets stuck there, probably because it waits for the color subsystem which is not there yet.
